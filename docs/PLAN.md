# 奖杯截图工具：需求与实现规划

## 1. 一句话目标

选一个目录（某款游戏的全部奖杯录像），逐条播放、按帧微调到想要的画面、截一帧存 PNG，自动进入下一条，直到全部处理完；可中断、可续做。

## 2. 用户已确认的硬约束

- **禁止 Electron / 任何 WebView 方案**，必须是原生窗口框架（2026-11-10 用户明确拒绝）。
- 视频解码、截图允许使用 FFmpeg 系方案（ffmpeg / ffprobe / libmpv / libvlc 均可）。
- 只在 Windows 桌面跑，无需跨平台。
- **原片只读**：不移动、不重命名、不删除、不改写录像文件。
- 现有工作流是「手动用 mpv 逐帧截图」，新工具的帧行为应与 mpv 一致，不能引入新的帧精度风险。

## 3. 素材实测（`F:\Video\FF共鸣`，2026-11-10 抽样）

| 项 | 实测值 |
| --- | --- |
| 文件数 | 40 个 `.mkv` |
| 总体积 | 58 GB |
| 单文件大小 | 约 340 MB – 880 MB |
| 分辨率 | 2560×1440 |
| 编码 / 封装 | H.264 / Matroska |
| 帧率 | **CFR 60/1**，`r_frame_rate == avg_frame_rate`（抽样 6 个文件全部一致） |
| 时长 | 296–300 秒 |
| 帧数 | 17894 帧（≈ 时长 × 60） |
| 首帧 PTS | 0.000 / 0.017 / 0.033 / 0.050 / 0.067（严格 1/60 间隔） |
| 单帧 PNG | 约 1.4 MB |

**推论**：素材是恒定帧率，帧号 = `round(时间 × 60)`，理论上不需要逐帧索引。但代码仍要在加载时校验 `r_frame_rate == avg_frame_rate`，不等时退化为慢速探测（见 §4）。

## 4. 关键工程结论：不要把 ffmpeg 当"按需截图器"

实测同一台机器、同一个 1440p60 文件：

| 操作 | 耗时 | 说明 |
| --- | --- | --- |
| 起一个 ffmpeg 精确 seek 取单帧 | **1.94 s** | 进程启动 + 从关键帧解码 |
| `ffprobe` 全量列举每帧 PTS | **72 s** | 逐帧扫描，不能用 |
| `ffprobe` 读元数据 | 毫秒级 | 可以随便调 |

所以：
- **不能每次步进都 spawn 一个 ffmpeg 进程**，1.94 秒一帧比手动 mpv 还慢，方案直接失败。
- **不能为每个文件建全量帧索引**，40 个文件 × 72 秒 = 48 分钟。
- 需要**常驻解码器**持续输出帧，UI 只消费解码后的帧。

## 5. 技术选型

**结论：视频内核用 mpv（libmpv / mpv 子进程），通过 IPC 控制；UI 框架自选原生方案。**

理由：现有工作流就是 mpv，`frame-step` / `frame-back-step` 逐帧、`screenshot-to-file` 截当前帧（原生分辨率）都是 mpv 的既有能力，帧语义与用户现在手动操作完全一致，验收风险最低。mpv 对 mkv/H.264/1440p60 的支持和硬解都成熟。

**架构**：

```
┌─────────────────────────────┐
│ 原生 UI（列表 / 时间轴 / 按钮）│
└──────────┬──────────────────┘
           │ JSON IPC（命名管道 \\.\pipe\...）
┌──────────▼──────────────────┐
│ mpv 进程（--wid 嵌入 UI 窗口）│  ← 逐帧、seek、截图都由它执行
└─────────────────────────────┘
           │ 仅用于元数据探测
┌──────────▼──────────────────┐
│ ffprobe（取时长/分辨率/帧率） │
└─────────────────────────────┘
```

关键点：**因为控制走 IPC，UI 语言可自由选择**，不需要为 mpv 写绑定。

**UI 框架候选**（由下游决定，但必须先做 spike）：

| 方案 | 优势 | 风险 |
| --- | --- | --- |
| C# WPF / .NET 8 | `HwndHost` 嵌 mpv 有成熟做法；打包简单；用户有 WPF 经验 | 需要 C# |
| Java / JavaFX | 用户主语言 | 拿 HWND 嵌外部窗口要手工做（JNA），跨 DPI 有坑 |
| C++ / Qt | 最稳 | 开发成本最高 |

**M0 必须先验证的 spike**（做不成就要换方案，别写完 UI 才发现）：用 `--wid` 把 mpv 嵌进目标框架的窗口，确认能正常渲染、能响应键盘、退出时不留孤儿进程。备选内核是 libvlc（`next_frame` + `take_snapshot`），但换了内核就要重新做 §9 的帧精度验收。

## 6. 功能与交互

### 6.1 列表

- 选目录后扫描 `*.mp4 *.mkv *.mov *.webm *.m4v`，按文件名自然排序（注意 `Replay 2026-10-22 00-01-37` 这种命名，按时间字符串直接排序即可）。
- 每行显示：文件名、时长、状态（已完成 / 未处理 / 出错）。
- 顶部显示进度 `已处理 3 / 40`。
- 完成的判定：`screenshots/<同名>.png` 存在。

### 6.2 播放与定位

- 打开即暂停，显示首帧。
- 水平时间轴可拖动，拖动时显示目标时间的画面。
- 显示当前位置：`mm:ss.mmm` + `帧 7985 / 17894`（帧号来自 mpv 的 `estimated-frame-number`）。
- 粗调（±1 秒）与精调（±1 帧）分开，因为 5 分钟内找画面基本是先粗后精。

### 6.3 快捷键（核心功能，不是附加项）

| 键 | 作用 |
| --- | --- |
| `←` / `→` | ∓1 帧 / ±1 帧 |
| `Shift+←` / `Shift+→` | ∓10 帧 |
| `,` / `.` | ∓1 秒 |
| `空格` | 播放 / 暂停 |
| `Enter` 或 `S` | 截当前帧 → 保存 → 自动进入下一条 |
| `Backspace` | 重截当前条（覆盖已有 PNG） |
| `↑` / `↓` | 切换录像（不截图） |

### 6.4 截图

- 输出 **PNG，原始分辨率 2560×1440**，不做缩放、不加水印、不做有损压缩。
- 文件名 = 录像主文件名 + `.png`（一视频对一图，幂等，重截即覆盖）。
- 落盘后刷新列表状态并自动切下一条（并定位到首帧）。

## 7. 目录与状态

```
<游戏目录>/
├── Replay 2026-10-22 00-01-37.mkv    原片，只读
├── ...
└── screenshots/
    ├── Replay 2026-10-22 00-01-37.png
    └── .state.json                   断点续做
```

`.state.json` 只记录：当前处理到哪个文件、最后确认的列表顺序、上次位置。已完成的判定仍以 PNG 是否存在为准（状态文件丢失也能自愈）。

## 8. 错误处理（必须显式，不能崩）

| 情况 | 行为 |
| --- | --- |
| 目录里混入非视频文件 | 按扩展名过滤，忽略 |
| 文件名含中文、空格、括号 | 全程参数数组传子进程，禁止拼命令行字符串 |
| ffprobe 解析失败 / 无视频流 | 列表标红，跳过继续，末尾汇总报告 |
| 目标 PNG 已存在 | 默认视为已完成；重截需显式操作（Backspace） |
| mpv 进程异常退出 | 提示并允许重开，不丢列表与已处理状态 |
| 磁盘写入失败 | 明确报错，不静默跳下一条 |
| 文件帧率非常数（VFR） | 载入时检测 `r_frame_rate != avg_frame_rate`，提示"逐帧可能不精确"，退化为按时间戳步进 |

## 9. 验收标准

1. **帧精度**：生成烧了帧号的测试视频，任取帧号 N，`→` 一次再截图，得到 N+1 帧；连续 ±1 往返后回到原帧，画面一致。

   ```sh
   ffmpeg -f lavfi -i color=c=black:s=640x360:r=60:d=10 \
     -vf "drawtext=text='%{frame_num}':fontsize=72:fontcolor=white:x=(w-tw)/2:y=(h-th)/2" \
     -c:v libx264 -g 60 -crf 18 test_frames.mkv
   ```

   人工核对前 20 帧、中段随机 5 帧即可，不必上 OCR。

2. 处理完一个目录后，`screenshots/` 中 PNG 数量与视频数一一对应。
3. 中途强制关闭再打开，从上次位置继续，不重复处理已验证条目。
4. 目录里放一个损坏的 mkv，程序不崩，标红跳过，其余正常。
5. 中文 + 空格文件名的录像能正常截图落盘。
6. 连续处理 5 个 1440p60 文件后内存不持续增长（帧缓冲有释放）。
7. 单次 `→` 到画面更新的延迟 < 100 ms（这是相对手动 mpv 的核心体验指标）。

## 10. 里程碑

- **M0（spike，半天）**：mpv `--wid` 嵌入目标框架 + IPC 通路，能 `--wid` 渲染、能发 `frame-step`、能 `screenshot-to-file`。做不成就换内核/框架，再继续。
- **M1**：目录扫描 + 列表 + 打开文件 + 时间轴 + ±1 帧 + 截图 + 自动下一条。跳过所有花活。
- **M2**：快捷键完整、断点续做、错误处理、进度显示。
- **M3**：打包成免安装 exe（自带 mpv + ffprobe），在一台干净机器上验证。

## 12. 明确不做

视频剪辑/转码/拼接、自动识别奖杯跳出时刻、多游戏管理、数据库、云同步、图片后期（裁剪/去黑边/加水印）、动图导出、批量重命名录像。
